# Agent Factory v0.2: Execution Sandbox Design

| | |
| --- | --- |
| Status | **Approved with amendments** (2026-10-01), implementation in progress |
| Baseline | `v0.1.0` = `8cfcd55fc45417ce4a00655710ab67efbaeda04e` |
| Scope | Isolating untrusted, AI-generated project code when it is executed |

The orchestrator (executor, agents, gateway, workspace, logs) stays trusted
and runs outside the sandbox.

## Approval amendments (binding)

These amendments override anything below that conflicts with them.

1. **DockerBackend** is the primary security backend for untrusted code.
   Untrusted code requires isolation level **CONTAINER or stronger**.
2. **No fallback** from container isolation to ordinary subprocess execution,
   ever.
3. If a qualifying backend is unavailable, unhealthy, misconfigured, or fails
   its isolation self-test, **the code is not executed** and the run moves to
   the resumable **`blocked`** state.
4. The `SandboxBackend` abstraction is preserved so other strong backends can
   be added later.
5. All v0.1 safety controls are preserved.
6. **Copy-in execution only.** The host project is never bind-mounted.
7. Docker networking is disabled for untrusted execution.
8. The host environment is never inherited wholesale.
9. Sandbox cleanup must be verified. Failure to verify cleanup is an
   infrastructure/security failure and blocks further untrusted execution.
10. Docker image pulls, builds, or updates never happen automatically during
    an agent run. Image creation is an explicit, human-initiated operation.
11. **The Windows Job Object work (former stage S3) is dropped from v0.2.**
    `LocalProcessBackend` remains for deterministic **trusted fixtures only**
    and is **never** an acceptable sandbox for real-model-generated code. This
    is explicit in code, tests, and documentation.
12. Infrastructure failures **block** the run. They do not consume developer
    repair retries.
13. v0.2.0 is **not tagged** until a separately authorized live adversarial
    acceptance phase (section 8, Tier 1) demonstrates containment.

Approved decisions: the `blocked` status; the trust model (FakeProvider
fixtures may use the local backend, everything else needs a container);
copy-in only; one-time human-run image build; default limits (120 s, 1 CPU,
512 MB, 256 MB scratch, 128 pids, 1 MB output per stream, 2 concurrent
executions).

## 1. Threat model

**Trusted:**
- the orchestrator
- the human operator
- template-authored files: scaffold, protected tests, test command

**Untrusted:**
- anything a model writes into a workspace
- anything that code does when executed

The execution surface is `RunTestsTool`.

| # | Threat | Primary control | Backstop |
| --- | --- | --- | --- |
| 1 | Reads outside workspace | Separate container root fs; workspace copied in; no bind mounts | No host paths exist in the container |
| 2 | Writes/deletes outside workspace | No bind mounts; read-only root fs; writes only to tmpfs, discarded | Nothing is copied back |
| 3 | Network | `--network none` | Self-test confirms only `lo` exists; `NetworkPolicy` has one value (`none`) |
| 4 | Child-process escape | PID namespace; container kill ends every process in it | `--pids-limit`, `--init`, `no-new-privileges`, `--cap-drop ALL` |
| 5 | Infinite loops | Host-side monotonic deadline, then `docker kill` | `--ulimit cpu` |
| 6 | Excessive CPU | `--cpus` | Concurrency semaphore |
| 7 | Excessive memory | `--memory` = `--memory-swap`; OOM detected via inspect | tmpfs usage counts toward the same cgroup |
| 8 | Excessive disk | Read-only root; size-capped tmpfs `/work`, `/tmp`; `--ulimit fsize`; `--log-driver none` | Staging size/count caps; output caps |
| 9 | Env/credential leakage | Container env built only from explicit allowlisted `NAME=value` pairs | Secret-like names rejected; no Docker credentials or config inside |
| 10 | Symlink/junction/traversal | Staging accepts regular files only (`lstat`; links, junctions, reparse points, hardlinks rejected); relative POSIX names | The container has no host mounts |
| 11 | Surviving process trees | `docker rm -f` ends the PID namespace; removal is verified | Labels + janitor; backend unhealthy if unverified |
| 12 | Malicious test commands | Command comes from the template only; argv, no shell; interpreter allowlist | It runs inside the sandbox anyway |
| 13 | Concurrent interference | Unique name/labels per execution; no shared volumes or tmpfs | Semaphore; janitor removes only expired or orphaned containers |
| 14 | Sandbox failure → unrestricted execution | No fallback; unavailable/failing → denied, run `blocked` | Isolation-level gate on every request; the local backend refuses untrusted code itself |

**Also covered:**
- a remote Docker context or `DOCKER_HOST` would be external communication, so it is rejected
- image pulls are network access, so `--pull never` is always set and the image is verified by ID
- hostile output is capped and decoded with replacement characters

**Out of scope for the sandbox** (see section 10): test-verdict forgery,
kernel exploits, Docker Desktop vulnerabilities.

## 2. Architecture

```
 trusted (Windows host)                                                  untrusted
 ┌──────────────────────────────────────────────────────────────┐
 │ TesterAgent → ToolGateway (policy, approvals, log)            │
 │      → RunTestsTool (adapter)                                 │
 │          → SandboxManager                                     │
 │              • trust → required isolation level (fail closed) │
 │              • explicit backend list, no downgrade            │
 │              • health, janitor, self-test, semaphore          │
 │              → SandboxBackend ──────────────────────────────────► container
 │                  prepare / execute / collect_result / destroy │   (no mounts,
 │          ← ExecutionResult → test report (+ sandbox block)    │    no network)
 └──────────────────────────────────────────────────────────────┘
```

Package `agent_factory/sandbox/`:

| Module | Responsibility |
| --- | --- |
| `types.py` | Requests, limits, results, enums, error hierarchy |
| `validation.py` | Request validation (argv, env, limits, paths) |
| `process.py` | Bounded subprocess runner (monotonic deadline, capped output) |
| `base.py` | `SandboxBackend` ABC and `run_sandboxed()` (destroy always runs and is verified) |
| `manager.py` | `SandboxManager`: policy gate, health, janitor, self-test, semaphore |
| `local.py` | `LocalProcessBackend`: isolation `NONE`, trusted fixtures only, **not a sandbox** |
| `fake.py` | `FakeSandboxBackend` test double (runs nothing) |
| `staging.py` | Safe workspace snapshot → in-memory tar |
| `docker.py` | `DockerBackend`: hardened argv builder, context validation, inspect mapping, cleanup |

## 3. Backend comparison

Startup figures are estimates and will be measured during live testing.

| Criterion | Docker Desktop (WSL2) | Windows Sandbox | WSL2 distro + bubblewrap | Hyper-V VM | Pure Python / subprocess |
| --- | --- | --- | --- | --- | --- |
| Filesystem | Strong; copy-in | Strong; disposable VM | Weak by default (`/mnt/c`); acceptable only hardened | Strongest | **None** |
| Network | `--network none` | `<Networking>Disable` | Shared NIC; per-run `--unshare-net` | No vNIC | **None** |
| CPU | `--cpus`, `--ulimit cpu` | None per run | cgroup v2 / prlimit | vCPU + limit | Job Object (not in v0.2) |
| Memory | `--memory` + OOM detection | `<MemoryInMB>` | cgroup | VM RAM | Job Object (not in v0.2) |
| Disk | Read-only root + capped tmpfs | No quota | Capped tmpfs | Fixed VHDX | None |
| Process | PID namespace, pids limit | Whole VM | bwrap PID namespace | Whole VM | No namespace |
| Startup (est.) | ~0.5–1.5 s warm; 10–60 s cold | ~10–30 s, single instance | ~1–3 s cold | 20–60 s | ~0.05 s |
| Cleanup | `rm -f` + labels + janitor | Discarded on close | Namespace dies | Revert/delete disk | Stray files persist |
| This machine | Installed; may be stopped | **Unavailable (Home)** | Available | **Unavailable (Home)** | Yes |
| Automation | Low | Medium-high | Medium-high | High | Low |
| Dependencies | Docker Desktop + local image | Win Pro/Ent | WSL + new rootfs + bwrap | Win Pro + admin + image | None |
| Escape risk | Shared kernel in the Desktop VM; misconfiguration is catastrophic (argv golden-tested, context checked) | Mapped writable folder | Interop and `/mnt/c` unless disabled | Strongest | **Not a boundary** |
| Suitability | **Primary** | Future (Pro machines) | Future equal-level backend | Future high-assurance/CI | **Trusted fixtures only** |

Also considered: Windows AppContainer. Rejected for v0.2 because it needs ACL
changes to the Python install, has no disk limit, and is complex to drive
from Python.

## 4. Primary backend: DockerBackend

**Image.**
- `agent-factory/sandbox-python:3.12`, built locally from a committed
  Dockerfile based on a digest-pinned `python:3.12-slim`
- the image **ID** is configured; containers are created from that ID with
  `--pull never`
- the image is built only by an explicit human-run command, in a later,
  separately authorized stage

**Container flags** (golden-tested; also checked at runtime before every
`docker create`):

```
docker --host <validated local endpoint> create --pull never --name af-<execution_id>
  --label agent-factory.exec=<id> --label agent-factory.run=<run_id>
  --label agent-factory.owner=<process token> --label agent-factory.deadline=<epoch>
  --network none --read-only --cap-drop ALL --security-opt no-new-privileges:true
  --user 10001:10001 --init --ipc private --log-driver none --hostname sandbox
  --pids-limit <pids> --cpus <cpus> --memory <mem>m --memory-swap <mem>m
  --ulimit cpu=<s>:<s> --ulimit fsize=<bytes>:<bytes> --ulimit nofile=256:256
  --tmpfs /work:rw,noexec,nosuid,nodev,size=<disk>m,uid=10001,gid=10001,mode=0700
  --tmpfs /tmp:rw,noexec,nosuid,nodev,size=64m,uid=10001,gid=10001,mode=0700
  --env NAME=value ...  --interactive
  <image id> af-entry --workdir <rel> -- <argv...>
```

**Forbidden before the image reference:**
- bind mounts of any kind (`-v`, `--volume`, `--mount`, `--volumes-from`)
- `--privileged`
- host networking or any network other than `none`
- host PID/IPC/UTS/userns namespaces
- `--cap-add`, `--device`
- port publishing, `--gpus`, `--runtime`, `--sysctl`, `--env-file`
- a bare `-e NAME`
- any Docker socket or engine pipe reference
- a root user

**Copy-in.**
1. The orchestrator stages a deterministic tar in memory and streams it on
   stdin of `docker start --attach --interactive`.
2. `af-entry` extracts it into `/work` (tmpfs).
3. `af-entry` then runs the argv with stdin closed.

Nothing is copied back to the host.

**Probe** (read-only CLI calls):
- engine reachable, server OS linux
- effective endpoint (`DOCKER_HOST` or context) is a **local** named pipe or
  unix socket
- configured image ID present locally

**Self-test** (live): a hardened container proves:
- uid 10001
- only `lo` exists
- `/` is not writable
- `CapEff == 0`
- env names are only the allowlisted ones

All later commands pin `--host` to the validated endpoint, and `DOCKER_*`
variables are stripped from the CLI environment. The backend refuses any
Docker subcommand outside a fixed allowlist, so `pull`, `build`, `run`,
`login` and `push` cannot be issued.

## 5. Fail-closed policy

- **Isolation levels:** `NONE` < `PROCESS` < `CONTAINER` < `VM`.
- **Code trust:**
  - `ModelProvider.produces_trusted_code` defaults to `False`; only
    `FakeProvider` declares `True`
  - the executor marks the workspace `untrusted` before running any node with
    an untrusted provider
  - workspace trust never goes from `untrusted` back to `trusted_fixture`
  - a missing or unreadable trust record counts as untrusted
- **Required level:** untrusted needs `CONTAINER` or higher; trusted fixtures
  may use `NONE`.
- **`LocalProcessBackend` is never eligible for untrusted code.** The manager
  rejects it, and the backend itself refuses untrusted requests.
- **Backend selection** follows an explicit configured list. Only backends at
  the required level are considered. A backend that is unavailable or
  unhealthy is skipped in favour of another qualifying one, never a weaker
  one.
- **No qualifying backend:** `SandboxUnavailable` / `ExecutionDenied` is
  raised and the run goes `blocked`. No process starts.
- **Cleanup that cannot be verified:** `SandboxCleanupError`. The backend is
  marked unhealthy and the run goes `blocked`.
- **Limits hit by the code** (time, memory, cpu, disk, pids, output): a real
  test failure (`fail`), with the reason passed to the developer.

## 6. Interfaces

See `agent_factory/sandbox/types.py` and `base.py` for the implemented
interfaces:
- `ExecutionRequest`: workspace, command, working dir, limits, network
  policy, explicit env + allowlist, trust
- `ExecutionResult`: stdout, stderr, truncation flags, exit code, timeout and
  limit status, backend info, duration, cleanup verification
- `SandboxBackend`: `probe`, `self_test`, `prepare`, `execute`,
  `collect_result`, `destroy`, `janitor`

## 7. Execution lifecycle (DockerBackend)

1. **Gate.** Validate, map trust to a level, choose a backend, check health,
   run the janitor and self-test on first use, then take the semaphore.
2. **Stage.**
   - walk the project with `lstat`; accept regular files only
   - reject symlinks, junctions, reparse points, hardlinks, special files,
     unsafe or reserved names, and anything that resolves outside the project
   - re-check identity with `fstat` after opening each file
   - enforce size and count caps
   - build a deterministic tar
3. **Prepare.** Build the argv, run the hardened check, `docker create`.
4. **Execute.**
   - `docker start -a -i` with the tar on stdin
   - capped output readers
   - monotonic deadline; on deadline or output overflow, `docker kill`
5. **Collect.** `docker container inspect` gives `ExitCode`, `OOMKilled`, and
   `Error`; these map to status and limits hit.
6. **Destroy (always).** `docker rm --force --volumes`, then verify that no
   container with the execution label remains.
7. **Janitor.** Remove containers whose deadline label has passed, or whose
   owner token is this process but which aren't active, then verify.

## 8. Test strategy

**Tier 0** runs everywhere: no Docker, no network, no containers. It covers:
- validation
- staging escape attempts
- the hardened argv (golden + forbidden-flag checks)
- context validation
- the inspect/result mapping
- the cleanup model
- the subcommand allowlist (never pull/build)
- the fail-closed manager
- BLOCKED/resume
- trust tracking
- that the local backend is not a sandbox

An autouse guard fails any test that tries to launch a `docker` executable.

**Tier 1** is live Docker. It needs separate authorization and is required
before tagging v0.2.0. It must demonstrate containment against:
- outside-workspace reads and writes
- network access
- host env/secret access
- infinite execution and surviving child processes
- excessive memory and disk
- process/fork exhaustion and output flooding
- concurrent-run interference
- malformed/traversal input
- cleanup after success, failure, timeout, and resource exhaustion

`pytest --require-sandbox` turns Tier-1 skips into failures.

**Tier 2** is manual and periodic: adversarial review and a Docker Desktop
settings audit.

## 9. Migration from the v0.1 `RunTestsTool`

1. The test command becomes backend-neutral (`python -m unittest ...`). Each
   backend resolves `python`.
2. `RunTestsTool` builds an `ExecutionRequest` and calls the
   `SandboxManager`. The test-report fields are unchanged; a `sandbox` block
   is added.
3. New action category `execute_sandboxed` for `run_tests`; the tester-only
   allowlist is unchanged.
4. The executor gains the resumable `blocked` status and a `run_blocked` log
   event. State schema goes v1 → v2, and v1 checkpoints are upgraded on load.
5. All v0.1 controls are unchanged.

## 10. Unresolved risks

1. **Container escape.** Containers share the Docker Desktop VM kernel, and
   an escape lands in a VM that can reach Windows drives. No Enhanced
   Container Isolation on the personal plan. Accepted for v0.2.
2. **Test-verdict forgery** by generated code. The sandbox protects the host,
   not the honesty of the result.
3. **Docker Desktop configuration drift.** The self-test catches part of it.
4. **Availability.** Docker Desktop may be stopped; runs block (safe but
   disruptive).
5. **Base-image supply chain.** The first pull is human-run; digest pinning
   protects later runs.
6. **The orchestrator parses untrusted data.** Staging and output parsing are
   capped.
7. **Trust misclassification.** Defaults are untrusted and trust never
   resets.
8. **tmpfs counts toward the memory limit.**
9. **Host sleep.** Monotonic deadlines are used.
10. **Not yet verified live:**
    - the `af-entry` stdin handoff
    - `--log-driver none` combined with attach
    - startup overhead

## 12. Implementation deviations (recorded at pre-release)

The approved design above is kept as written. The implementation differs in
these places; [../sandbox.md](../sandbox.md) describes the shipped behaviour.

| Area | Design said | Implemented | Why |
| --- | --- | --- | --- |
| Copy-in | `af-entry` reads the tar to EOF | Reads exactly `--archive-bytes` and verifies `--archive-sha256` | Independent of Docker's stdin-EOF semantics; integrity check |
| Staged input | Up to `disk_mb` | ≤ min(½ `/work`, ¼ memory), in tmpfs pages | Keeps writable headroom; af-entry buffers the archive in memory |
| CPU-time limit | `--ulimit cpu=<s>:<s>` | Soft `<s>`, hard `<s>+2`; optional explicit `cpu_time_s` | With soft = hard the kernel sends SIGKILL, so a CPU-limit hit was misreported (found by live testing) |
| af-entry failures | Reserved exit codes 120–123 | Every af-entry failure, including unexpected exceptions, uses them | An uncaught exception once exited 1 and looked like a project failure (found by adversarial testing) |
| Default routing | Docker becomes the default in a later stage | `SandboxManager.default()` = `[LocalProcessBackend, DockerBackend(approved image)]`; untrusted code can only use Docker | As approved for the pre-release |
